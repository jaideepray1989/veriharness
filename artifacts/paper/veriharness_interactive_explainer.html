VeriHarness: Deep Interactive Explainer

This page is intentionally self-sufficient: it explains the paper’s claim, the exact runtime structure in this repository, how each policy variant behaves, how data is produced, and where to contribute first.

Paper thesis in one view

VeriHarness separates generation from acceptance. The leaf model proposes outputs; code-owned gates decide acceptance. On failure, the controller can retry with either untyped feedback or typed failure-conditioned repair.

H0: full trace + self accept H3: state context + external gates generic-retry: external gates + untyped retry H4: external gates + typed repair + candidate retention
Key practical conclusion: - Typed repair is NOT a blanket replacement for generic retry. - Under low call budgets (1-2), gains are small. - Under sufficient budget (4), typed repair can be large, mostly on multi-step verifiable workflows. - Single-step controls show little uplift.

Runtime control plane (actual repo structure)

Orchestrator.run() -> _load_tasks() -> schedule_tasks(variant-major) -> run_task_variant(task, variant) if variant.uses_external_gates: _run_gated() for attempt in range(max_retries+1): if leaf_calls >= call_budget: break context = build_context_pack(..., retry_feedback) candidates = min(_candidate_count(variant), remaining_budget) for candidate in candidates: output = _run_leaf() passed, gate_results = _run_gates() if passed: return success retry_feedback = _repair_feedback(...) else: _run_self_accept() -> ExperimentResult row appended to results.jsonl

Oracle-blind vs oracle-guided acceptance (critical)

In oracle-blind mode (evaluation.oracle_guided_acceptance=false), oracle is post-hoc only. The orchestrator explicitly filters post-hoc oracle failures out of retry feedback.

# orchestrator.py (conceptual) if not oracle_guided_acceptance: oracle_result = evaluate_oracle(task, output) oracle_result.metadata["used_for_acceptance"] = False oracle_result.metadata["evaluation"] = "posthoc_oracle_blind" results = results + [oracle_result] def _repair_visible_results(results): # drop posthoc oracle result from repair feedback in blind mode ...

Benchmarks, matrix design, and row production

Task families

  • context_trace: invariant retention under distractors.
  • provenance_bias: reject/repair wrong claims under provenance framing.
  • mini_workflow: artifact + invariant preserving workflows.
  • Public NLP controls: BoolQ, SQuAD, SciQ, ARC-Easy, GLUE SST-2/RTE/MRPC, TREC-QC.

Practical matrix per budget config

  • Per seed: 150 leaf + 30 workflow = 180 tasks
  • Seeds: 3 → 540 tasks
  • Variants: 4 (H0, H3, generic-retry, H4)
  • Rows per budget run: 2160
  • Oracle-blind primary path by config flag
How one results.jsonl row is produced
1) Load config + generate tasks from benchmark generators 2) Scheduler emits (variant, task) 3) Orchestrator runs task variant (self-accept or gated/retry) 4) Build ExperimentResult with: - success flags - retry/call counts - failure reasons - model + budget metadata 5) Append row to run_dir/results.jsonl

High-impact contribution roadmap

Code-first paths

  1. Refine typed repair payload granularity in core/repair_policy.py.
  2. Add new deterministic checks/gates for richer workflow verifiability.
  3. Improve candidate selection heuristics while preserving budget fairness.
  4. Add richer run metadata that explains why a retry path succeeded.

Test-first paths

  1. Add explicit oracle-guided metadata assertions.
  2. Add tests for oracle filtering in blind-mode retry visibility.
  3. Add H1 context-pack regression tests (summary vs raw trace).
  4. Add multi-failure ordering tests for typed feedback stability.
  5. Expand family-specific retry guidance assertions (e.g., SQuAD/MCQ).
Suggested first PR (small, high-value): 1) choose one failure code family (e.g., artifact/evidence) 2) improve typed feedback text for one benchmark family 3) add/adjust tests in test_repair_policy + test_experiment_runner 4) verify behavior separation between generic-retry and H4 remains intact

Bottom line

VeriHarness is best understood as a controllable runtime policy experiment: generation is model-side, acceptance is code-side, and typed repair is a conditional advantage when task structure and budget support repair.
